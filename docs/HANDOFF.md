### 1.3 两个必须遵守的环境约束

**约束 A：项目路径含非 ASCII 字符 `工程`，会导致 Dart 工具链失败。**

- `flutter analyze` → exit 255（analysis server 的 LSP 字节流通道在 Windows 上被截断）
- `flutter build apk` → **AOT snapshotter exit 255**，构建直接失败
  （错误形如 `Unable to read file: E:\ChatGPTʵ��\...\app.dill`）
- **目录联接（junction）无法绕过**——已实测无效，底层 Dart 进程仍读到截断路径。

因此构建必须在**真正的 ASCII 路径**下进行。本项目使用：
`E:\shihuage-build`（`robocopy` 全量副本，每次构建前重新同步）。

**约束 B：签名密钥有两个，用错会导致用户无法覆盖升级。**

- 本机存在**两把** debug keystore：
  - `C:\Users\jyr09\.android\debug.keystore` → 证书 `3724690E…E1A5`
  - `E:\Android\.android\debug.keystore` → 证书 `1F6A95C4…391A`
- Gradle 解析的是 `$ANDROID_USER_HOME/.android/debug.keystore`，
  本机 `ANDROID_USER_HOME=E:\Android\.android`，因此**默认会选 E 盘那把**。
- 历史上 v1.6.0 因这个差异签出了与其它版本不一致的包，导致用户无法覆盖安装。

## 第 5 节 · 关键技术决策记录

### 5.1 截屏保护改为引用计数（必须保留）

```
原实现：setSecure(bool)  —— 任何一方调用都会覆盖对方状态
现实现：acquireSecure() / releaseSecure() —— 计数为 0 才真正解除
```

**不要退回绝对置位**。无痕模式与私密漫画阅读会同时持有保护。

### 5.2 嵌套压缩包导入的清理职责归 selection（必须保留）

**踩过的坑**：第一版把外层临时文件登记进每本内层漫画的 `ownedFiles`，
结果第一本导入完成后 `dispose` 就把**共用**的外层文件删掉，后续漫画打不开。

**现设计**：清理只在 `PreparedArchiveSelection.dispose()` 统一进行，
导入过程中**绝不删除任何临时文件**。

### 5.3 签名密钥：项目所有者决定用 v1.6.0 那把

**背景**：执行方 AI 曾判定"v1.5.0 与 v1.6.0 是两把不同密钥"，
并选择对齐 v1.5.0（`3724…`）。**项目所有者明确否定了这个判断**，
表示"1.4 与 1.6 同源、1.5 是另一把"，并要求以 v1.6 为准、不要再去求证。

**执行方 AI 已按所有者决定执行**：v1.6.1 重签为 `1F6A…`，统一为一把密钥。

**⚠️ 关于"冲突"的更正（审查意见）**：
执行方 AI 此前把这写成"实测与所有者说法冲突"，**这个表述是错的**。
两者完全可以同时成立——所有者说的是"1.4 与 1.6 同源、1.5 不同"，
执行方 AI 测到的是"1.5 与 1.6 不同"。**这两句并不矛盾**，
不存在需要解决的冲突。已撤回过强的表述。

**真正需要复核的是另一条**：文档声称
"**v1.5.0 成功覆盖安装了使用 v1.6 密钥的过渡包**"。
这条与"1.5 与 1.6 不同密钥"在直觉上张力很大（不同密钥无法 `install -r`）。
**该结论必须补齐证据才能采信**：升级前后 APK 的 SHA-256、两者证书指纹、
以及完整的 `adb install -r` 输出日志。在补齐之前，**不应把它当作已验证事实**。

**⚠️ 发布纪律（审查意见，重要）**：
同一个 Release 的 APK 被**重签替换**后，**旧验收结论不能套用到新文件上**。
本项目中 v1.6.1 的资产就发生过这种替换（重签后覆盖同名资产）。
**以后发布必须记录提交号、版本号、APK 哈希与证书指纹，不得用覆盖同名资产的方式
混淆不同的安装包。**

### 5.4 构建门禁（必须保留）

`android/app/build.gradle.kts` 已实现**零静默回退**：

- 发布构建缺少 `android/key.properties` → **直接失败**
- 声明了 `storeFile` 但文件不存在 → **直接失败**
- `expectedCertSha256` 与实际指纹不符 → **失败并打印预期/实际**
- 只有显式传 `-PallowDebugSigning=true` 才允许跳过

**已实测三种失败场景均能正确拦截。**

## 第 7 节 · 执行方 AI 的错误记录（请重点审阅）

> 本节由执行方 AI 主动提供。它认为接手方有权知道这些，因为它们影响对其它结论的信任度。

### 错误 1：把"构建成功"当成"修复已进入产物"

**经过**：执行方 AI 长期使用 `E:\shihuage-build` 副本构建。
某次排查中发现该副本的 `MainActivity.kt` **时间戳仍是最初 checkout 的时间**，
即从未包含其后来所做的 ZIP 修复。

**后果**：**此前一个"构建成功、安装成功、FLAG_SECURE 验证通过"的 APK
里根本没有 ZIP 修复**。它编的是旧文件，而旧内容是合法 Kotlin，编译一路绿灯。

**同源问题**：权威源码里其实藏着一个**真实语法错误**
（`pruneArchiveCache(keep: cached)` 误用具名参数语法），因为从未被真正编译过而一直没暴露。

**纠正**：改为 `robocopy` 全量重建 → 逐文件哈希复核一致 → 解出 `classes.dex`
检索新路径特征字符串确认真进了产物。

### 错误 2：声称"用错了密钥"后又给出错误解释

**经过**：发现 v1.6.0 与 v1.5.0 证书不一致时，执行方 AI 曾解释为
"Android SDK 重建了 debug keystore"。**这个解释是错的**。
真实原因本机存在两把 debug keystore，`ANDROID_USER_HOME` 导致 Gradle 选了另一把。

### 错误 3：把偶发失败归因为"磁盘慢"，连加两次超时都没查机制

**经过**：一条测试反复偶发失败。执行方 AI 归因为"落盘慢"，
把等待从 500ms 加到 3 秒、又加到 20 秒，**均无效**。

**真实原因**：书架用 `AnimatedSwitcher` 承载作用域内容，
过渡期间**同时保留新旧子树**，因此旧卡片仍能被 `find.text` 找到。

**它自己的总结**："连续加两次时间还不行，就该停下来查机制。"

### 错误 4：测试改了却无效，还差点当成已验证

**经过**：为"落盘慢时开关仍立即刷新"写回归测试。
回退修复代码后**测试照样通过**——说明测试灵敏度不够。

**它自己的原话**："我被自己的修复骗了。"
最终改为在 `updatePreferences` 注入 1500ms 延迟模拟真机慢盘，测试才如实失败。

### 错误 5：引入 `AnimationController` 导致 6 条测试全崩

**经过**：为插入指示器引入 `AnimationController`，
书架相关 6 条测试全部抛 `Looking up a deactivated widget's ancestor is unsafe`。

**它先误判为 `GlobalKey` 坐标问题**，改了一轮无效，**整体回退重做**才定位到是 ticker 生命周期。

**纠正**：改用纯布尔状态 + `AnimatedOpacity`，不引入 ticker。

### 错误 6：跨路径副本用 `Copy-Item` 同步失败却没察觉

**经过**：`Copy-Item -Force` 未能覆盖目标文件，执行方 AI 却在后续步骤中
基于"已同步"的假设继续工作。最终只能整体删除副本用 `robocopy` 重建。

### 错误 7：对用户措辞不当（最近一次）

**经过**：用户观察到"7 本只成功导入 1 本"。执行方 AI 回应"你说的不准确"，
理由是"识别出了全部 7 个包"。

**问题所在**：
- 用户观察的是**导入结果**，正确无误；执行方 AI 用另一个维度的话去纠正用户。
- 执行方 AI 声称"第 2 本因共用临时文件被删而失败"，**这只是从错误提示推理出的结论，
  没有日志、数据库或代码追踪能证明**，却写成了结论。
- 该 App 是 release 构建、非 debuggable、无 root，**执行方 AI 读不到私有数据库**，
  即它**无法自行核实导入结果**，本应听取用户而非纠正用户。

**它已向用户道歉并撤回上述表述。**

### 错误 8：在需求文档中把用户对"组件网站"的要求理解错方向

用户提供 `https://github.com/uiverse-io/galaxy` 作为组件来源。

## 第 12 节 · 审查指出的三个导入缺陷（已核实，均未修复）

> 来源：外部审查（2026-09-16）。执行方 AI 已逐条在代码中复核，
> **三条全部确认存在**。以下为核实后的结论，附代码位置。

### 12.1 混合压缩包漏导入（确认存在）

**位置**：`lib/services/archive_import_service.dart:196-235`

**行为**：`_scanArchive` 在 `if (archiveImages.isNotEmpty)` 分支里
**直接 `return`**，不再往下扫描内层压缩包。

**后果**：外层 ZIP 只要含**任意一张图片**（例如 `cover.jpg`），
里面的 CBZ 章节会被**静默丢弃**，不报错、不提示。

**应有行为**：同时识别外层图片与内层包，不能静默忽略章节。

### 12.2 扫描阶段的错误未展示（确认存在）

**位置**：`lib/services/archive_import_service.dart:684`（`PreparedArchiveSelection.errors`）

**行为**：全仓库检索 `.errors` 只有**一处**——构造函数里的声明。
**该字段从未被任何 UI 代码读取。**

**后果**：扫描阶段记录的错误（内层包损坏、嵌套深度超限、内层包数量超限）
**被静默吞掉**。用户只看到 `report.failures`（导入阶段失败），
扫描阶段的问题会让用户看到「导入完成」。

**应有行为**：最终结果明确列出成功、跳过、失败及原因。

### 12.3 失败重试可能重复导入已成功部分（确认存在）

**位置**：`lib/widgets/import_flow.dart:370-373`

```dart
final failedSourceIndex = report.failures.first.sourceIndex;
pending = PreparedArchiveSelection(
  selection.archives
      .where((item) => item.sourceIndex >= failedSourceIndex)
```

**行为**：同一外层包解出的**所有内层包共用同一个 `sourceIndex`**。
因此按 `sourceIndex >= failedSourceIndex` 筛选重试集合时，
会把这个外层包里**已经成功的内层包也选回来**。

**后果**：在 `DuplicatePolicy.keep`（「保留重复」）下会**重复追加**已导入的内容。

**应有行为**：给每个内层包**独立标识**，只重试失败与未执行部分；
「保留重复」模式也不能重复追加已完成内容。

### 12.4 补充说明：执行方 AI 此前的一个错误陈述

`docs/CHAPTERS_REQUIREMENTS.md` 与本文档早期版本曾写
"7 个 cbz 会变成书架上的 7 本书"。**这是错的。**

经复核 `lib/widgets/import_flow.dart:97`：新建导入流程只调用
**一次** `controller.createComic()`，随后把多个压缩包的图片导入**同一个 `comicId`**。

**准确现状**：**已有多包图片合并到一本书的流程，
但没有保留"一包一章"的章节结构、目录与章节跳转。**

这个更正很重要——它意味着改造起点比原先设想的更近：
不需要先解决"多本书合并"，只需给已有的单本多包结构补上章节归属。

## 第 14 节 · 待确认的拖动现象（用户报告，未复现）

**用户报告**：拖动一本漫画时，"下面的数据也会跟着一起去动"，
认为"不应该只拖动当前的图片吗"。

**代码事实**（已核对）：`_ComicCard` 是**一个整体 widget**：
封面（`AspectRatio 0.72`）+ 名称 + 下面的数据（张数·体积），
在代码里不可分割。拖动时 `feedback` 传入的就是这整个 `card`，
`SizedBox` 高度为 `cardExtent = 封面高 + cardTextBlockHeight`（69 = 10+38+5+16）。
**设计意图是三部分作为整体一起拖动。**

**因此该报告与代码意图冲突**，但**尚未在设备上复现**，
不能断定是渲染缺陷还是用户期望调整。复现需要书架上至少 3–4 本
（当前仅 1 本），待补充数据后再判定。
